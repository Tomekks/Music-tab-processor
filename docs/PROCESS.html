If Muse is down (step 4 or 5)
  1. Script retries Muse once.
  2. Still down: script stops and prints "Muse down, recommend deepseek-v4.1-flash, switch?".
  3. Claude asks you. On yes it re-runs with the other model; the report names which model built it.
  4. Never a -free model, never a silent switch.
Guard rails on Claude's side
  1. Two failed builder runs that are not a provider outage: stop and report. No more plumbing debugging.
  2. Decision gate after one real task: if it fails twice for non-provider reasons, drop opencode and use a Claude Haiku subagent.
  3. The only record that matters is the task file; the raw log is a fallback.

Why the checks sit after the build, not before: a script looking at what actually changed cannot be fooled by a model's own summary, and it is cheap. Long lists of "you may not do X" rules are fragile and cost more to maintain. Removed from the old design: the opencode reviewer, the roughly 40-rule permission list, the permission test script, the separate health-check script.

2. What could go wrong, and the safety net

⚠ Cheap model writes weaker briefs than Claude.
Net: you approve the "what changes for you" box, a review level checks it, and the first two tasks are an experiment with a scorecard.
⚠ A useful old rule gets lost in the move.
Net: every rule line goes in a ledger first; a script checks the new files still contain it; old docs stay in place during a trial; a pre-lean snapshot and backup archives exist.
⚠ The shorter report hides a problem.
Net: it keeps "decisions the spec didn't settle" and "not run" lines, and the checker prints raw counts.
⚠ A fresh cheap model ignores or never sees a rule.
Net: a short executor file, few absolute rules in AGENTS.md, and "stop and ask" written into the task file.
⚠ A cheap-model review (Level 1) misses something.
Net: risky work (data, deletes, contracts, deploys) always gets Claude at Level 2.
⚠ Extra setup friction (separate code copies need their own setup, ports and env files).
Net: one small setup script, planned.

4. Reports by kind of task

Every report has the same four lines: commit, change summary, checker output, "decisions the spec didn't settle".

KindAdds
Small fix (copy, style)nothing
Featureone line per acceptance check, plus your checklist
Bug fixroot cause with evidence, plus the test that failed before
Layout / UIPlaywright layout checks (measurements for overflow and overlap, plus pixel comparison against a baseline you approved), plus your checklist. No model looks at images.
Risky (data, deletes, contracts)the exact lines that guard it, plus a risk-to-test map

After every task: one scorecard line (passed first try? fix rounds? did your own test fail?).

7. Rules everyone follows

Prefer the simple solution (does it need to exist → reuse → built-in → one line → only then new code). Use a script before reasoning where one can answer (search, count, check). Say plainly what was not checked. Change only what the task needs. You say yes before push, deploy or delete. Limits: about 10 new tests per task, verify in about 60 s, two failed attempts then stop, rule files stay under their line caps.

8. If you feel something is missing

  1. Tell me a keyword or the situation.
  2. I search the old rules (the pre-lean snapshot) with one command and show you where it lived.
  3. We decide together; the rule is added back and logged in docs/work/missed.md.
