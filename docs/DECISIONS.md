# Decisions

The reasoning behind how this project is built, not just what was chosen. Written to be self-contained — if you're an AI agent picking this up cold, this file plus `docs/ARCHITECTURE.md` and `docs/AUDIOPROCESSINGTOOLS.md` should be enough to understand *why* things are the way they are, not just what the current state is. Don't re-litigate anything here without a concrete new reason — these were arrived at deliberately, over several rounds of back-and-forth, not defaults.

## The core reframe: recognizable, not accurate

The goal is "what's the easiest way for a beginner guitarist to play something recognizably close to this song" — not a note-perfect transcription of the original recording. This isn't a lowered bar for its own sake; it's what makes several otherwise very hard problems tractable. A guitar-only, pixel-perfect source separation is a hard, partly unsolved problem; "notes that sound like the riff when played on a guitar" is a much easier target, and it's the one that actually matters here — musicians learn songs by ear and approximate them constantly, and tabs are copyrighted anyway, so an approximation was always the honest goal, not a compromise. Concretely, this reframe is why vocal separation quality was later declared explicitly out of scope (see below) — vocals don't need to be clean, they just need to not contaminate the guitar/melody content enough to confuse transcription. Keep coming back to this framing whenever a technical decision threatens to get complicated: the question is never "is this the real sound," it's "would this let someone play something that sounds like the song."

This project also has a second, explicit purpose: it's a public demonstration of the developer's ability to direct AI tools, as a designer, not a professional software engineer. That's why the repo structure and documentation quality matter as much as the running app — the repo itself is part of the deliverable.

**What stays local-only, and why.** Source audio, separated stems, MIDI transcriptions, generated tab data, and reference images (`research/00_spike/audio/`, `output/`, `fretboard/`) are excluded from the public GitHub repo (see `.gitignore`). A MIDI or tab derived from a copyrighted song is a derivative work in the same category as a tab itself — fine to keep and use locally, not something to publish. Only the text analysis describing what was tried and found (`RESULTS.md`, `README.md`) is public, since it doesn't reproduce any song's actual content.

**Using existing published tabs as a validation aid, never as a pipeline input.** When judging Phase 0 output by ear, comparing it against a known, already-published tab for that song sharpens the judgment beyond "does this sound roughly right." This is different from feeding existing tabs into the pipeline itself, which would defeat the project's purpose — most songs someone actually wants to learn won't already have a tab, so the pipeline has to work without one.

## Local-first, hosted later, and why the Mac is never exposed to the internet

The processing pipeline (separation → transcription → tab generation) runs only on the developer's own Mac, indefinitely — not because hosting it is impossible, but because free serverless hosting tiers (Vercel/Netlify) are built for requests that finish in seconds, not multi-minute ML inference with multi-GB models. Trying to run Demucs or Basic Pitch inside a hosted serverless function on a free tier would fight the platform, not use it well.

What can move online later is a separate, light, read-only web app that renders already-generated tabs. The two sides — local pipeline, hosted app — are deliberately never connected to each other directly. The developer was explicit about this: their Mac must never be made reachable from the internet (no open ports, no tunnels like ngrok) under any circumstances without a real conversation about the tradeoffs first, because that's real attack surface for comparatively little benefit. Instead, the two sides meet only at a shared, hosted database: the Mac writes a row when a song finishes processing, the hosted app only ever reads rows. This is also why a database was wanted "from day one" even before there was an obvious use for it — it turned out to be the mechanism that makes hosting possible later without ever compromising the developer's own machine, and it doubles as tab history (every processed song stays available without re-running the pipeline). See `docs/ARCHITECTURE.md` for the visual version of this split (and a link to the live "Signal Path" diagram).

**Database choice (2026-09-08): Turso, accessed through Drizzle ORM.** "Local SQLite for now" (the original phrasing above) turned out not to actually work once the hosted app became real — a SQLite file on the developer's Mac is exactly the kind of thing that machine being unreachable from the internet prevents Vercel from ever reading. The database itself has to be genuinely hosted. Compared against Cloudflare D1 specifically: D1 is only natively reachable from inside Cloudflare Workers, so using it from a Vercel-hosted app would mean standing up a *separate* Cloudflare Worker just to proxy requests to it — real added infrastructure for no benefit here. Turso (hosted, SQLite/libSQL-compatible) connects directly from Vercel's serverless functions like a normal database client, has a genuinely generous free tier (5GB storage, 500M reads/month) built specifically for this exact pattern (a local/edge writer, a read-heavy hosted app), and was compared against `sqlite.ai`'s equivalent offering, whose free tier is explicitly positioned as a "prototypes and demos" trial (512MB storage, no backups) rather than a stable long-term free option. Turso's own durability story is strong independent of any free-tier concern: continuous S3-backed replication, 90-day point-in-time restore. Drizzle ORM sits in front of it specifically so a future migration to a different backend (Postgres, D1, etc.) is a contained config/schema change, not a rewrite — the same "swappable components" principle already used for the audio pipeline, applied to data storage.

**What's actually stored, and what deliberately isn't:** one row per published song — title, tempo, tuning, and the tab's notes (string/fret/timing) as JSON. Never audio, stems, or MIDI, for the same copyright reasoning as everywhere else in this project (a MIDI or audio file is a much more direct reproduction than a text tab). Since this project has no auth (a from-day-one choice — "no auth, no monetization, no export"), whatever's published is effectively public once hosted — worth being deliberate about which songs actually get shown on a live, shareable link, since a hosted, always-on tab occupies the same legal gray area as any unofficial tab website, just now visibly attributable to the developer specifically rather than sitting only on their own machine.

**Vercel auto-deploy-on-push turned off, and staging/versioning/live kept as three separate gates (2026-09-08).** Connecting Vercel to GitHub for convenience had a real cost that only showed up once it was actually relied on: every push — including pure doc edits — triggered a real build, and a Vercel project setting (Root Directory) being wrong caused three consecutive deployments to fail before anyone noticed, because nothing was actually watching each one. Free-tier build minutes are a real, finite budget for a project with no revenue, and "deployed" was never something that should happen as a side effect of "committed." The fix (`app/vercel.json`'s `git.deploymentEnabled: false`) fully decouples the three things that had been silently bundled together: a **local staging build** (`npm run stage` — the real production build, run locally, free, answers "does this actually work") is separate from a **GitHub push** (versioning — answers "does a version of this exist") which is separate from a **Vercel deploy** (`vercel deploy --prod`, run manually from the repo root — answers "is this the one that's actually live"). Each answers a different question the developer explicitly wants answered separately, so no model working on this repo should collapse any two of them into one step, or push/deploy without asking which of the three is actually wanted — see `AGENTS.md`'s "Previewing and shipping a change to `app/`" for the binding procedure this produced.

**Standing rule, not just a preference:** any future change that would make this machine reachable from the internet — inbound access of any kind — requires stopping, laying out the actual tradeoffs, and getting an explicit yes before proceeding. This is written into `AGENTS.md` as a hard rule for exactly this reason. Outbound requests (a package install, a normal API call, a tool fetching a webpage) are a different, much lower-stakes category and don't need the same gate — but per the safety principles below, they should still be explained before they happen.

## Component choices, and why they're built swappable rather than picked once

Each pipeline stage was chosen with an explicit understanding that it will likely be replaced or supplemented later, and the architecture is built around that from the start rather than treating swaps as future refactors:

- **Separation:** `htdemucs` first (stable, mature, well-documented), with `htdemucs_6s` (adds dedicated `guitar`/`piano` stems) and `mlx-demucs` (Apple-Silicon-native, same weights, faster) as documented next steps. `mlx-demucs` specifically needs to run on real macOS with Apple's MLX framework — it cannot be tested from a sandboxed/bridged environment, only from a real local Terminal.
- **Transcription:** Basic Pitch first (lightweight, fast, trivial to install), with MT3 / MR-MT3 (research-grade, specifically documented in the literature as better on low-resource instruments like guitar, but much heavier to set up) as a known fallback if Basic Pitch's accuracy on distorted guitar isn't good enough.
- **Tab generation:** `tuttut` first (already does fingering optimization via a Hidden Markov Model, minimizes hand movement — a good beginner-friendly default), with `open-fret` (a newer, more sophisticated transformer-based approach) as a documented swap-in once it matures past its current early-stage limitations, and `gtrsnipe`/`tayuya` as other found alternatives.

**Why swappable, and what that costs:** designing one clean interface that any backend for a given stage can plug into is cheap and worth doing from the start — it's what turns "try a different separation tool" into a small, isolated task instead of a rewrite. Actually installing and wiring up every candidate tool before there's a real reason to is not cheap — each one drags in its own dependencies, disk footprint, and testing burden for a benefit that might never materialize. So the rule is: one interface per swappable stage, one real implementation behind it now, additional implementations added one at a time, only when there's a concrete reason, and — this was an explicit request — **each swap-in is preceded by a fresh, deeper research pass on that specific alternative at the time it's actually being considered**, not by reusing whatever comparison was made earlier. `docs/AUDIOPROCESSINGTOOLS.md` exists specifically to support this: it's a running catalog of everything found for each stage (tried or not, with notes), kept up to date, so a research pass starts from what's already known rather than from zero — but an entry existing there is not a substitute for actually doing that fresh pass before adopting it.

**Vocal separation quality is explicitly out of scope**, discovered as a natural consequence of the "recognizable, not accurate" reframe above: the goal is guitar/melody content for tabs, not clean vocals, so vocal-isolation-focused tools (e.g. BS-Roformer via `audio-separator`) are deprioritized relative to guitar-isolation-focused ones (`htdemucs_6s`'s dedicated guitar stem). Vocal bleed only matters to the extent it contaminates the guitar/melody signal enough to confuse transcription — it is not something worth separate effort to clean up for its own sake.

**Song complexity, not audio quality, is the transcription bottleneck — and simpler songs are the near-term target.** Phase 0 testing (Checkpoint 2) found that separated and full-mix transcription both broke down on dense, distorted, multi-instrument sections of the two test songs, while a third, fully acoustic solo-guitar song transcribed cleanly with no separation needed — with source audio quality ruled out as the cause (the harder songs were already high-quality 320kbps AAC). Rather than chasing better results on full-band/distorted songs right away, the decision is to treat simpler/acoustic material as the realistic near-term target and revisit harder songs later, once the rest of the pipeline (tab generation, the app) is proven end-to-end on material it already handles well. This isn't a permanent limitation, just a sequencing choice — the same logic as backlogging riff auto-detection: prove the easier case first.

**Priority, stated explicitly (2026-09-07): get a full, working, end-to-end MVP first — separation through a real app a song can be practiced from — before iterating on the weakest individual stage.** This governs sequencing whenever there's a choice between polishing a component further (e.g. chasing better transcription on hard songs) versus moving the pipeline forward to its next unproven stage. Breadth-first, not depth-first: the acoustic-song success above is what makes this possible now rather than blocking on it.

**Concrete sequencing decision (2026-09-07, tightened 2026-09-08):** build toward a working end-to-end MVP using the Mister Sandman success (simple acoustic material) as the proof case, rather than immediately returning to Checkpoints 4 (does riff-trimming help) and 5 (second full comparison on Friction) — both of which are about improving results on the harder, full-band songs. Those checkpoints are deferred, not abandoned. **Explicitly confirmed trigger condition:** revisit them only once *both* the local processing pipeline *and* a hosted UI are done — not just the pipeline working locally. The reasoning is external to this codebase: this project doubles as a job-search portfolio case study, and the priority is a complete, shippable, demonstrable loop over chasing quality on the hardest inputs — which may not even be fully solvable with current tools ("maybe with a future AI model, who knows").

## Manual riff identification, and what's deliberately backlogged

Identifying "where the main riff happens in a song" automatically is a genuinely hard, partly-unsolved music-structure-segmentation problem. Rather than attempt to automate it for v1, the developer marks the riff section manually in a simple player — this was a deliberate choice, not a fallback: understanding the process firsthand was explicitly preferred over automating it away immediately. Auto-detection remains a possible later upgrade, not a blocked one.

Several other features are intentionally out of scope for now, each for a specific reason rather than as a blanket "later": **difficulty grading** (Original/Medium/Easy/Baby) is backlogged because it needs its own real design work (what makes a tab objectively easier — note density, fret span, position changes, technique complexity) that hasn't been done yet, and doing it prematurely risks building on a pipeline that might still change shape. **Spotify metadata lookup** and **"check if tabs exist online"** are backlogged because they're quality-of-life additions for a tool that, by design, serves one user who already knows what they uploaded — not worth the complexity yet. **`yt-dlp` (YouTube-link ingestion)** is backlogged because file upload alone is enough to validate the core pipeline, and adding a second ingestion path before the first is proven just adds a dependency and a failure mode (YouTube's page structure changing) for no immediate benefit — it's sequenced explicitly *after* Phase 0 succeeds, not abandoned. When it is eventually built, it's for the developer's own internal exploration of a wider range of songs — **never for demos or anything published.** Source-audio licensing is a separate, real concern that doesn't go away by choosing `yt-dlp` over a local file — stream-ripping copyrighted audio doesn't have a clean legal answer regardless of source, and for a *public* demo specifically, the answer is to use royalty-free/Creative-Commons-licensed audio instead (e.g. YouTube Audio Library, ccMixter, Free Music Archive), sidestepping the question entirely rather than trying to resolve it.

**Local web UI for triggering pipeline runs (backlogged, 2026-09-07).** Rather than a pure CLI, the local pipeline will eventually get a simple local-only web UI — click a button, pick an audio file, kick off processing. Worth planning for even though it's not being built yet: it doubles as the natural entry point for `yt-dlp` ingestion later (paste a link instead of picking a file), and removes the need to touch a terminal for day-to-day use. Resources gathered for when this gets built: [Lucide](https://lucide.dev/icons/) for icons, the `anthropics/claude-code` [frontend-design plugin](https://github.com/anthropics/claude-code/tree/main/plugins/frontend-design) guidelines, and Paul Bakaus's [`impeccable`](https://github.com/pbakaus/impeccable) design-quality guidance. A real design system (swappable colors/shapes/spacing/etc., not hardcoded values) is wanted from the start once this is built. Open question, not decided yet: same Next.js app as the hosted read-only practice view (different route) vs. a separate local-only tool.

**Playback** in practice mode plays back a synthesized version of the transcribed notes, not the original recording — chosen because listening to the full original song while trying to learn a riff is distracting for a beginner who hasn't learned it yet; a metronome defaulting to the song's tempo but adjustable down is part of this for the same reason.

**Backlogged addition to playback (2026-09-07):** a visual cue highlighting which note/chord is currently sounding during playback — reading a tab alone doesn't convey the melody, and sometimes you have to hear it to play it accurately. This reconciles cleanly with dropping per-note timing from the tab data itself: overall tempo (one number) is still needed for realistic playback pacing, but exact per-note timing for synthesis can come from Contract A's originally-timed notes rather than being duplicated into the tab representation — a plain tab display and a timed playback feature don't need to share the same timing precision.

**Display modes are layered, and ASCII is the default, not a placeholder.** The plain ASCII tab is the baseline output — always available, always correct in content, independent of any richer view existing yet. Additional display modes (a visual fretboard diagram, note-highlighting during playback, chord-name references for a song) are opt-in layers on top of the same underlying note/chord data, built one at a time, each independently swappable without affecting the others — the same "one interface, swappable implementations" principle already used for the processing pipeline, extended to how results get shown.

**First opt-in display layer built (2026-09-08): a fretboard diagram** (`app/components/FretboardDiagram.tsx`), shown below the ASCII tab on a song's page. Reads the same `tab.schema.json` note data, no pipeline changes needed — exactly the swappable-layer design above, proven out for real.

**Revised the same day, after using it: a static "every position at once" overview turned out not to be useful, replaced with a sequenced strip.** The first version deduped every unique string/fret position into one diagram — deliberately not showing order, on the theory that "where does this song live on the neck" was useful on its own. Tried against a real song, it wasn't: knowing *where* a note is without knowing *when* it comes doesn't actually help someone find it while playing. Replaced with one small mini-fretboard **per playback step**, chained left to right in the order they're actually played — the same order the ASCII tab already shows, now drawn on the neck instead of just implied by column position. Simultaneous notes (same `startTimeSec` — a chord) are grouped into one step, not split into several, exactly the concern flagged when this was still a future idea: two notes only ever played together would otherwise misleadingly render as two separate steps. The thin-e/thick-E top toggle carries over to every segment. Verified against a real song with hundreds of steps (Mister Sandman, 766) — rendered and interacted correctly, no performance issue.

**Revised again, same day, after using it a second time: segments moved from a fixed-width window to a tight fit.** Every segment initially showed a fixed 4-fret window regardless of content — padded, and wasteful of horizontal space for the common case of a single note. Changed to: a segment's window is exactly the fretted span played, no padding — a single note is 1 cell wide, a narrow chord isn't padded out, an open-only step shows 1 cell of context instead of 4 empty ones. Segment width becomes a visual signal on its own now (a wider segment means an actual stretch), which wasn't true of the fixed-width version. Also removed the fret number drawn inside each note dot — redundant with the column header above, which is the only place it needs to live now that segments are tightly fit rather than a uniform size. The specific rendering rules (and a running log of ones not yet decided) live in `app/components/FretboardDiagram.RULES.md`, a small file meant to be added to over time rather than growing indefinitely inside this one.

**Songsterr explored as a reference for richer display (2026-09-08), and why it's inspiration, not a near-term target.** Songsterr's synced notation+tab+lyrics view with a YouTube play-along was looked at directly as a possible direction. Two real, structural gaps, not just "more work": (1) its rhythm notation (stems/rests/beaming precisely on the beat) needs exact per-note duration, which this project deliberately does not capture — `tab.schema.json`'s `durationSec` is approximated as "time until the next note," confirmed acceptable earlier specifically because exact rhythm was decided to be the human's job, not the tab's; matching Songsterr here would mean reopening that decision, not adding a display mode on top of it. (2) YouTube play-along needs a video-ingestion/metadata path this project doesn't have — `yt-dlp` is explicitly backlogged for real licensing reasons (see below), so this isn't just unbuilt, it's blocked on a decision already deliberately deferred. The part of this idea that *is* cheaply compatible with what's already decided: a moving highlight on the existing tab as it plays — that's the already-backlogged "visual cue highlighting the currently-sounding note," synced to the synthesized playback this project already plans, not to a YouTube video. Logged here so this doesn't get re-explored from zero later.

**The compatible part of the Songsterr idea, built (2026-09-09): "Sheet"** (`app/components/SheetDiagram.tsx`) — a tab staff visually inspired by Songsterr, deliberately scoped to only the part that doesn't conflict with the `durationSec`-approximation decision above: 6 lines, notes as round shapes with the fret number inside, positioned in playback order, no rhythm notation (no stems, no beaming, no note-duration-proportional spacing). Not real musical staff notation — Songsterr itself shows a real notation staff *and* a tab staff together; this only builds the tab-staff half, which is the half this project's data actually supports well. What's genuinely missing versus the full Songsterr reference (rhythm notation, technique markers the schema already carries but nothing draws yet, bar lines, chord-name labels, lyrics) is logged in `SheetDiagram.RULES.md`, not silently dropped.

**Song display modes are now genuinely swappable, not just designed that way: three real views, one screen, switched by tab (2026-09-09).** `app/components/SongTabs.tsx` — Sheet, Fretboard, Ascii, in that order (Sheet is the default), controls below the song's title/tuning header, exactly one view visible at a time rather than all three stacked vertically on the page. This is the "opt-in layers" principle from earlier in this section, now actually exercised with three real implementations instead of one.

**The metronome (2026-09-09) partially answers the "playback-synced highlighting" idea logged above — deliberately partially, not as an oversight.** Built as `app/hooks/useMetronome.ts`: a generic step sequencer (play/pause, editable bpm, advance one step per beat, loop) with zero knowledge of notes, strings, or frets — the same "keep layers separate" principle from `AGENTS.md` applied to *when* something happens, not just *what*. It does not attempt to sync to the song's actual note timing; it advances one step per beat at whatever bpm is set, full stop, matching the same "recognizable, not accurate" reasoning at the top of this file rather than trying to solve real rhythmic sync — which would run into the same `durationSec`-approximation limit the Songsterr note above already covers. Because the hook is generic, any display mode could consume its `currentStep` — today only `SheetDiagram` does (a dashed playhead line, inverted note colors at the active step); extending the same highlight to `FretboardDiagram` is real, logged, and cheap-looking, just not done yet.

## Stack: Next.js + TypeScript, and the reliability toolkit for cheap/free models

Several JavaScript frameworks would technically work for the eventual web app. Next.js's specific advantage here is that it's the most widely used React framework in existence — which matters because the actual implementation work is done by small, free/cheap coding-agent models (via OpenCode, with a cheap frontier model as fallback when a free one stalls). Those models have seen vastly more correct Next.js code in training than any less common alternative, meaning fewer hallucinated APIs and fewer subtly-wrong patterns. Next.js is also made by the same company as Vercel, minimizing friction for the free-tier hosting path planned for later.

TypeScript is part of the stack specifically as a reliability mechanism, not just convention — it's one piece of a broader answer to an explicit concern: the developer doesn't fully trust free/cheap models to produce correct output unsupervised, and wanted concrete things built in to catch mistakes rather than relying on manual review alone. The resulting toolkit, roughly in order of how cheap they are to set up versus how much they catch:

- **Type/schema checking at the module boundaries** (TypeScript on the app side, and the `contracts/*.schema.json` files checked as real, importable files rather than described only in comments or code) — the single highest-leverage item, because a model that violates the agreed data shape gets an immediate, automatic error instead of a silent bug discovered later by ear.
- **A test written alongside every task, not after** — ordinary unit tests where the logic is deterministic (guitar-logic modules), "golden file" comparisons against a known-good prior output where it isn't (ML pipeline stages), so a refactor that quietly breaks something is caught automatically.
- **Linting and formatting enforced automatically**, so output stays consistent regardless of which model or which day produced it.
- **A small CI check (GitHub Actions) running tests and linting on every commit** — an objective, always-on, boring signal that doesn't require reading every diff by hand.
- **Small, scoped commits/PRs per task** — makes it trivial to revert one bad chunk without losing everything around it, and keeps each unit of AI-generated work small enough to actually review.
- **An explicit, written "done when…" checklist in every task spec** (see `docs/specs/`) — most drift happens because a vague instruction left room to improvise; a concrete acceptance list closes that room.
- **Periodic "walk tests"** (see below) as a manual spot-check layered on top of all of the above, not a replacement for it.

## Why `icm-architect`'s structure is used selectively, not wholesale

`icm-architect` (github.com/RinDig/icm-architect) was the developer's own suggestion for a token-efficient, drift-resistant project structure, and it was seriously investigated — including reading its actual repository contents, not just its pitch. Three things came out of that investigation that led to selective adoption rather than wholesale adoption:

First, there is no software codebase to adopt wholesale in the first place — the repository is `README.md`, `SKILL.md`, a `references/` folder, and a `templates/` folder: a documentation/methodology package, not a working application with `src/`, a package manager config, or any framework-specific scaffolding. "Adopting it completely" would mean adopting a set of organizing *principles*, because that's the entirety of what exists.

Second, even as principles, the methodology is explicitly general-purpose — its own scope covers "processes and workflows, knowledge management, production pipelines, organizational structures, content work," not software engineering specifically. Its six structural forms (Pipeline, Umbrella, Record library, Knowledge bundle, Context map, System map) map unevenly onto a project this size: "Pipeline" fits the audio-processing stages well, "Record library" fits per-song tab history well, but "Umbrella" (multi-pipeline portfolios) and "Context map" (organizational graphs) are built for a scale and kind of problem a single-user hobby app doesn't have. Applying all six in full would mean inventing structure that isn't needed.

Third, and specific to this project's execution model: the coding agents doing the implementation are small, free/cheap models that have seen enormous amounts of idiomatic Next.js and Python project layout in training, and essentially none of this specific, low-adoption methodology. A wholesale, unfamiliar structural scheme is *more* foreign to a small model than the standard conventions it already reproduces reliably — which cuts against the exact "reduce drift and hallucination" reason the methodology was attractive in the first place. Next.js and Python tooling also have their own hard structural requirements (routing conventions, import/package layout) that this methodology doesn't address and can't override.

**What was actually adopted, deliberately, not as a hedge:** numbered folders to encode pipeline sequence (`pipeline/s01_ingest/`, `s02_separate/`, …), a small `STATUS.md` state file per stage so any reader — human or agent — can tell what's done without reading code, explicit "contract" files at module boundaries (the `contracts/*.schema.json` files), and the **"walk test"** habit itself: before considering a task finished, check whether someone with zero memory of this conversation could open the folder just touched and understand its purpose and status from its files alone. If not, the task isn't finished — the code might be, but the documentation of it isn't. These four mechanisms solve a real problem standard project layout doesn't address; the rest of the methodology was deliberately left out because it would add structure this project doesn't need.

**One concrete deviation from icm-architect's own spec, and why (2026-09-07):** `icm-architect`'s `SKILL.md` is explicit that sequenced folders should be named `01_`, `02_`, … (invariant #3, bare digit prefix). This project uses `s01_`, `s02_`, … instead. The reason isn't a sophistication tradeoff — it's a hard Python syntax rule: an identifier can't start with a digit, so `pipeline.01_ingest` is a `SyntaxError` for every model, not just weaker ones. If anything, a less capable model is *more* likely to write a normal `import` statement without knowing to work around it, so keeping the literal `01_` format would be the riskier choice for exactly the models this precaution is supposed to protect. The `s` prefix keeps 100% of the actual goal — order readable from a directory listing alone, at a glance, by any model — while making normal, standard-convention Python imports just work. This is the same "selective adoption" reasoning as above, applied to a specific case that reasoning didn't originally call out by name.

One mechanism from this methodology is now leaned on as hard as it usefully can be, because of a later, sharper requirement: this project needs to keep working no matter which AI model is doing the implementation, including ones that don't auto-load any particular filename convention. `icm-architect`'s central claim — that plain, committed files can carry enough state for a memoryless agent to orient correctly, without depending on any model's built-in configuration — is exactly the property that solves that. `START_HERE.md` at the repo root, and the broadened walk test in `docs/DRIFT_CHECK.md`, are that mechanism pushed as far as it goes. This doesn't reverse the reasoning above — the six structural forms are still not fully applied, for the same reasons — it's the one piece of the methodology that earns its place completely.

## Phase 0: throwaway scripts before any real app or pipeline code

Before any of the architecture above got built out as real, structured code, the core technical assumption — that this pipeline can actually produce something usable from real songs — got tested with short, disposable scripts (`research/00_spike/`), each answering one question, each judged by ear rather than by an automated metric. This ordering is deliberate: building repo structure, a database, or app code on top of an unproven transcription step would be spending real effort (and real AI-execution budget) on infrastructure for a pipeline that might still need to change shape. Nothing in `research/00_spike/` is meant to be imported by real pipeline code later — if something there proves out, it gets rewritten properly as a real pipeline stage, not promoted as-is.

## Safety & process principles — why they exist, not just what they say

`AGENTS.md` states these as rules; the reasoning behind them is worth keeping visible. The developer's core concern is that free/cheap models doing unsupervised implementation work could make unpredictable or harmful changes to their actual machine — not through malice, but through a small model taking a shortcut, misunderstanding scope, or "fixing" something that wasn't broken. The response to that concern isn't distrust of AI tools in general; it's specific, structural safeguards: changes stay minimal and scoped to what a task actually asks for; nothing makes this machine reachable from the internet without an explicit conversation first; outbound network requests beyond an ordinary package install get explained before they happen (what's being fetched, from where, why) so a large or unexpected download is never a surprise; changes prefer additive and reversible (a new file, a new Homebrew formula, a new virtual environment) over modifying shared system configuration; deletion permission is scoped to the specific case it was granted for, never assumed more broadly; and no model working on this project — Claude, Claude Code, OpenCode, or anything else — represents what it's doing inaccurately or downplays a risk. These aren't abstract best practices; they were arrived at directly from an explicit request to keep this machine safe from exactly the kind of "random, harmful" changes an unsupervised free model might otherwise make.
