# Task spec: Design system — component primitives (ColorField, Slider, SegmentedControl, Button)

Implements Task 4 of `docs/superpowers/plans/2026-09-19-design-system.md`. Read that task's
section first. Depends on Task 1 (`docs/specs/design-system-brand-data.md`), Task 2
(`docs/specs/design-system-resolver-and-build.md`), and Task 3
(`docs/specs/design-system-cutover.md`), all implemented and verified on
`task/design-system-brand-data` (not yet merged to `master`). Work from that branch.

**This is the first task that ships React/`.tsx` code in `packages/design-system`** (Layer 1,
design spec §1) and the first that needs `next.config.ts`'s `transpilePackages`. Tasks 1–3 were
additive and inert; this one is still additive (no existing file's *behavior* changes — nothing
in `app/app/` imports these components yet, that's Task 6), but it's the first time this
package's code, not just its data, has to satisfy the "no hardcoded design values" constraint
directly.

## 0. Two things verified while writing this spec that change what it asks for

Both were checked directly against the real code/toolchain, not assumed — see
`[[verify-review-claims-independently]]`.

**(a) `generateCSS()` does not make `component.*` tokens theme-aware.** Read
`packages/design-system/src/build-tokens.mjs` directly (lines 99–102): the `component.*` walk
emits every leaf into `:root` exactly once, resolved against the *base* (light) tree, with no
`[data-theme="dark"]` override counterpart the way `semantic.color` gets (lines 125–133 build
that override block only from `tokens.dark.semantic.color`). Concretely: `border`, `surface`,
`surfaceText`, `surfaceHover`, `surfaceActive`, and `surfaceActiveText` all differ between
`tokens.json`'s base `semantic.color` and its `dark.semantic.color` block — so a `component.*`
token that referenced any of those would silently freeze at its **light**-theme literal in
`:root`, with nothing to override it for `[data-theme="dark"]`. Since `data-theme="dark"` is
hardcoded on `StudioShell` and is the only theme ever rendered today (Task 1's spec, confirmed
again in Task 3's), any component consuming such a token would render the wrong color, silently,
every time.

Only `accent` and `onAccent` in `semantic.color` are genuinely theme-invariant (no entry in
`dark.semantic.color` for either), and nothing outside `semantic.color` (`state`, `focus`,
`radius`, `space`, `typography`, `layout`) has a per-theme variant at all in this schema.

**Rule this task follows:** a `component.*` token may only reference `accent`, `onAccent`, or a
non-color semantic section (`space`, `radius`, `typography`). Any place a component needs a
theme-varying color (`border`, `surface`, `surfaceText`, `surfaceHover`, `surfaceActive`,
`surfaceActiveText`), it consumes that color the same way `app/app/_components/*.tsx` already
does — the existing Tailwind utility class generated from `@theme inline`'s promotion of that
color (`border-border`, `bg-surface`, `text-surface-text`, `hover:bg-surface-hover`, etc.), which
*is* theme-aware because it resolves through the `[data-theme]`-scoped CSS variable, not a
component-specific alias. This isn't a workaround — it's the correct answer for a color a brand
already has one theme-aware name for; a second, non-theme-aware alias to the same role would be
strictly worse. **Do not extend `build-tokens.mjs` to fix this in general** — that's a real gap,
but fixing the build script for the general case is out of scope here (§2); this task routes
around it for the four specific components it ships.

**(b) `build-tokens.test.mjs` pins an exact golden CSS string that this task's new
`component.*` tokens will change.** `packages/design-system/src/build-tokens.test.mjs` asserts
`generateCSS(resolveBrandDir())` equals a literal `EXPECTED` string with an empty `component`
section's worth of output (no `--component-*` lines — `component` is `{}` today). Adding this
task's token blocks (§3.1) will add twelve `--component-*` lines to `:root`, which breaks that
test the moment `tokens.json` changes, unless `EXPECTED` is updated in the same commit. **The
plan's Task 4 file list doesn't mention this file — it needs to, and this spec's file allowlist
(§6) corrects that.** §3.2 gives the exact updated string, generated by running the real
`generateCSS()` against the exact token additions in §3.1 (not hand-derived), so there's no
guessing at kebab-case conversion or resolution order.

rule. Where each value comes from, and why:

| Token | References | Resolves to | Why this token, not a new literal |
|---|---|---|---|
| `colorField.swatchSize` | `semantic.space.6` | `24px` | No dedicated "icon/swatch size" scale exists; `space.6` is the closest existing token to a reasonable clickable swatch size, reused rather than inventing a new primitive for one control |
| `colorField.radius` | `semantic.radius.base` | `12px` | The only radius token in the schema — shared by the swatch and the hex input for one consistent rounding, not two guesses |
| `colorField.fontFamily` | `semantic.typography.mono` | `var(--font-geist-mono)` | DESIGN.md: "Geist Mono for anything numeric or tabular" — a hex color code is exactly that |
| `slider.accentColor` | `semantic.color.accent` | `#ae97f7` | Feeds the native `<input type="range">`'s `accent-color` (§4.2) — a real per-component override hook, not a redundant alias, since a brand could theoretically want a different slider accent than the global one later |
| `segmentedControl.gap` | `semantic.space.6` | `24px` | Matches `TabSelector.tsx`'s current `gap-6` exactly — same visual result, now token-driven |
| `segmentedControl.activeColor` | `semantic.color.accent` | `#ae97f7` | Matches `TabSelector.tsx`'s current `border-accent text-accent` for the active tab |
| `button.paddingX` | `semantic.space.3` | `12px` | Matches the existing `px-3` used by `MetronomeControls.tsx`'s buttons |
| `button.paddingY` | `semantic.space.2` | `8px` | No `6px` token exists to match those same buttons' `py-1.5` exactly; `space.2` (8px) is the nearest existing value, chosen over `space.1` (4px) for a better touch target — a deliberate deviation from the pre-existing pixel value, not an attempt to match it exactly |
| `button.radius` | `semantic.radius.base` | `12px` | The only radius token in the schema |
| `button.fontFamily` | `semantic.typography.sans` | `var(--font-geist-sans)` | UI text, per DESIGN.md |
| `button.primaryBackground` | `semantic.color.accent` | `#ae97f7` | First real use of `accent` as a *fill* rather than text/border emphasis — DESIGN.md already anticipates this ("used for... any future filled-background use") |
| `button.primaryText` | `semantic.color.onAccent` | `#141413` | DESIGN.md, same sentence: "Not yet used by anything in Phase 0; exists so Phase 1 has a contrast-safe answer already computed." This task is that Phase 1 use. Already contrast-tested (Task 2's `contrast.test.mjs`, `accent/onAccent` pair) — no new contrast test needed here |

Deliberately **not** added as `component.*` tokens (§0(a)): `colorField`'s swatch/input
border, background, and text colors; `slider`'s track color; `segmentedControl`'s border and
inactive-tab color; `button`'s secondary-variant background/text/border. All of these use a
theme-varying semantic color and are consumed directly via the existing Tailwind utility class
for that color instead (§4).

### 3.3 Styling convention for all four components (read before writing any of them)

Every visual property that has a token (§3.1, plus any color already promoted by `@theme inline`)
is consumed via a **Tailwind v4 arbitrary-value class bound to the CSS custom property** —
verified compiling correctly against this repo's actual `@tailwindcss/postcss` (v4.3.3) while
writing this spec, not assumed from general Tailwind knowledge:

- Color: `bg-[var(--component-button-primary-background)]`, `text-[var(--component-button-primary-text)]`, `border-[var(--component-segmented-control-active-color)]` — confirmed these resolve to `background-color`/`color`/`border-color` respectively (not, e.g., `border-width`, which the bracket syntax could plausibly have meant).
- Spacing: `px-[var(--component-button-padding-x)]`, `py-[...]`, `gap-[var(--component-segmented-control-gap)]`.
- Radius: `rounded-[var(--component-button-radius)]`.
- Native range accent: `accent-[var(--component-slider-accent-color)]`.
- Font family: `[font-family:var(--component-button-font-family)]` — **not** `font-[var(...)]`.
  Confirmed by direct test that the bare `font-[...]` arbitrary form resolves to `font-weight`,
  not `font-family` (Tailwind's ambiguity resolution for that utility prefix defaults to
  weight). The bracketed-property form (`[font-family:...]`) sidesteps the ambiguity entirely.
- A theme-varying color with an existing promoted utility (`border-border`, `bg-surface`,
  `text-surface-text`, `hover:bg-surface-hover`, `bg-surface-active`,
  `text-surface-active-text`) — plain class name, exactly as `app/app/_components/*.tsx` already
  uses them. No arbitrary-value syntax needed since these are already real Tailwind theme keys.
- Focus ring, on every interactive element these components render (buttons, the range input,
  the hex text input) — DESIGN.md specifies this and nothing in the app implements it yet
  (confirmed: no `focus-visible` usage anywhere outside `node_modules`), so this task is the
  first place it actually exists:
  `focus-visible:[outline:var(--focus-ring-width)_solid_var(--focus-ring-color)] focus-visible:[outline-offset:var(--focus-ring-offset)]`
  — confirmed compiling to real `outline`/`outline-offset` declarations, gated correctly on
  `:focus-visible` (not `:focus`, so a mouse click doesn't show the ring, only keyboard focus).
- Primary Button's hover state, per DESIGN.md's derived-not-hand-picked rule (design spec §3):
  `hover:[background-color:color-mix(in_srgb,var(--color-accent)_92%,var(--color-on-accent)_8%)]`
  (92%/8% = `1 - hoverOpacity`/`hoverOpacity`, `hoverOpacity` = `0.08`). Confirmed compiling —
  Tailwind v4 also auto-generates a `@supports (color: color-mix(...))` fallback, so no manual
  fallback is needed. Secondary Button's hover uses the existing `surfaceHover` token directly
  (`hover:bg-surface-hover`) instead of a color-mix — matching how the rest of the app already
  treats `surfaceHover` as its own literal, not a derived value (Task 1's spec).
- Anything with no token in this schema at all (border **width** — no `semantic.border.width`
  token exists; text size/weight — no typography-scale token beyond `sans`/`mono` *family*
  exists) uses Tailwind's own default scale as a plain class (`border`, `text-sm`,
  `font-semibold`), matching exactly what `MetronomeControls.tsx`/`TabSelector.tsx` already do
  for the same properties. This isn't a gap this task is responsible for closing — no token
  exists to reference instead.
- `value` passed into `ColorField`'s swatch background (`style={{ backgroundColor: value }}`) is
  the live color being edited, not a design-system value — a literal there is the field doing
  its job, not a constraint violation.

## 4. Components

### 4.1 `ColorField.tsx`

```ts
function ColorField(props: {
  value: string;
  onChange: (value: string) => void;
  onReset?: () => void;
  label?: string;
})
```

Swatch (a non-focusable `<span aria-hidden>`, sized `w-[var(--component-color-field-swatch-size)]
h-[var(--component-color-field-swatch-size)]`, `rounded-[var(--component-color-field-radius)]
border border-border`, `style={{ backgroundColor: value }}`) next to a text `<input>` (hex value,
`[font-family:var(--component-color-field-font-family)] bg-surface text-surface-text border
border-border rounded-[var(--component-color-field-radius)]` plus the focus-ring classes from
§3.3). `onReset`, when provided, renders a small text affordance
(`text-xs text-foreground/40 hover:text-foreground/70`, matching `TabSelector.tsx`'s existing
inactive/hover treatment of `foreground` — an opacity modifier on an already-tokenized color, not
a new hardcoded one) that calls `onReset` on click. `label`, when provided, renders as a
`<label>` wrapping the whole control (associates via nesting, no manual `id`/`htmlFor` needed).

### 4.2 `Slider.tsx`

```ts
function Slider(props: {
  value: number;
  onChange: (value: number) => void;
  min: number;
  max: number;
  step: number;
  label?: string;
})
```

A native `<input type="range" min={min} max={max} step={step} value={value} onChange={(e) =>
onChange(Number(e.target.value))} className="w-full accent-[var(--component-slider-accent-color)]
..."/>` plus the focus-ring classes from §3.3. Native range inputs already provide correct
keyboard behavior (arrow keys) and screen-reader semantics for free — no custom drag/pointer
logic needed for Phase 0, and none should be built (matches `AGENTS.md`'s "small reusable
functions," picking the minimal implementation that satisfies the interface). No custom track
styling — browser default track, `accent-color` themes the fill/thumb, which is sufficient for
Phase 0's decimal/pixel-value editing use case. `label`, when provided, renders as a `<label>`
wrapping the input, same as `ColorField`.

### 4.3 `SegmentedControl.tsx`

```ts
function SegmentedControl<T extends string>(props: {
  options: { value: T; label: string }[];
  value: T;
  onChange: (value: T) => void;
  ariaLabel?: string;
})
```

Generalizes `TabSelector.tsx` (read that file first) from a hardcoded `Tab` union to an
`options` array, keeping its exact structure: `role="tablist"`, one `role="tab"
aria-selected={...}` `<button>` per option, `-mb-px border-b-2` underline treatment. Container:
`flex gap-[var(--component-segmented-control-gap)] border-b border-border`. Active option:
`border-[var(--component-segmented-control-active-color)]
text-[var(--component-segmented-control-active-color)]`. Inactive option:
`border-transparent text-foreground/40 hover:text-foreground/70` — identical to `TabSelector`'s
current inactive treatment (§3.3 — an opacity modifier on `foreground`, no new token). Same
`px-3 py-2 text-base font-semibold transition-colors` structural classes as `TabSelector`, plus
the focus-ring classes from §3.3 (which `TabSelector` doesn't have today — new for this
component, not backported).

### 4.4 `Button.tsx`

```ts
function Button(props: {
  onClick: () => void;
  variant?: "primary" | "secondary";
  children: React.ReactNode;
})
```

`variant` defaults to `"secondary"`. Shared structural classes:
`inline-flex items-center justify-center gap-1.5 border text-sm font-semibold transition-colors
cursor-pointer rounded-[var(--component-button-radius)]
px-[var(--component-button-padding-x)] py-[var(--component-button-padding-y)]
[font-family:var(--component-button-font-family)]` plus the focus-ring classes from §3.3.

- `primary`: `bg-[var(--component-button-primary-background)]
  text-[var(--component-button-primary-text)] border-transparent
  hover:[background-color:color-mix(in_srgb,var(--color-accent)_92%,var(--color-on-accent)_8%)]`
  (§3.3 — the color-mix hover formula).
- `secondary`: `bg-surface text-surface-text border-border hover:bg-surface-hover
  hover:border-surface-hover` — the existing pattern from `MetronomeControls.tsx`'s buttons,
  with one deliberate correction: `border-border` instead of that file's `border-surface`. The
  `border` semantic role exists specifically for this (DESIGN.md: "hairline dividers and
  outlines"); `border-surface` there looks like a pre-existing inconsistency, not a convention
  worth propagating into this canonical component. Not a fix to that file — `MetronomeControls.tsx`
  is untouched (§2).

### 4.5 `index.ts`

Plain barrel:

```ts
export { ColorField } from "./components/ColorField";
export { Slider } from "./components/Slider";
export { SegmentedControl } from "./components/SegmentedControl";
export { Button } from "./components/Button";
```

Each component file starts with `"use client";` (all four use event handlers —
`onClick`/`onChange` — so each needs it independently; matches the existing precedent in
`StudioTabs.tsx`/`MetronomeControls.tsx`, both marked the same way for the same reason). The
barrel file itself does not need the directive.

## 5. Bad-case behavior

| Case | Required behavior |
|---|---|
| A `component.*` token in §3.1 is later changed to reference a theme-varying color (`border`, `surface`, etc.) | Not this task's problem to prevent going forward, but if it happens *during* this task, stop — that's exactly the bug in §0(a), reintroduced |

## 6. Forbidden patterns

- No hardcoded hex color, raw pixel value, or raw opacity number in any of the four component
  files — every such value must be a `var(--...)` reference (either a `component.*` token from
  §3.1, or an existing promoted semantic/Tailwind theme value), or (`ColorField`'s swatch only)
  the live `value` prop itself.
- No new `component.*` leaf that isn't a `{semantic.*}` reference (§3.1, §6.1's convention).
- No new `component.*` leaf referencing a theme-varying semantic color (§0(a)).
- No touching `resolve.mjs` or `generateCSS`'s resolution/emission logic — this task only adds
  data (§3.1) and updates the one test string that data changes (§3.2).
- No `disabled` prop, no pressed/`:active` styling beyond §3.3/§4.4's hover (§2).
- No touching `.env` or credentials.
