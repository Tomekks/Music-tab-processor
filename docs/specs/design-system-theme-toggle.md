# Task spec: Dark/light theme switcher (Task 4)

**Tier: S** — dev-only-adjacent but real end-user-visible UI, no real user data touched, fully
revertible via `git checkout`. Written fresh against `app/app/_components/StudioShell.tsx` (22
lines) and `app/app/_components/AppHeader.tsx` (13 lines) — if either has changed since, stop and
re-read before implementing.

## 0. User story

You open the app. It's always rendered dark, no matter your system preference. With this task, a
toggle in the header switches between light and dark, your choice persists across reloads (and if
you've never chosen, it follows your OS's own light/dark preference the first time), and every
view — Sheet, Fretboard, ASCII, the song list — reads correctly in both.

## 1. Context (read, don't re-derive)

- `build-tokens.mjs` already emits both `[data-theme="light"]` and `[data-theme="dark"]` CSS
  blocks from `tokens.json`'s base + `dark` blocks — confirmed by reading
  `app/app/design-tokens.generated.css` (gitignored, regenerated by `predev`/`prebuild`/`prestage`).
  `tokens.json`'s `dark` block already has real, distinct values, not placeholders. This task is
  UI + persistence only — no token/build work, don't let it grow into touching the generator.
- **The only thing hardcoding the app to dark-only** is `StudioShell.tsx:11`'s literal
  `data-theme="dark"` on the outer `<div>`.
- `AppHeader` (`app/app/_components/AppHeader.tsx`) is the one fixed landmark regardless of which
  song is selected — its own comment says so. It's the resolved home for the toggle, not a
  song-scoped component like `DetailToolbar.tsx` — don't reintroduce that as an option, it was
  already resolved in the plan.
- No existing `localStorage`-backed hook pattern in this codebase to reuse (checked
  `app/hooks/`, `app/lib/`) — this is a genuinely new, small pattern. `app/hooks/useMetronome.ts`
  is the closest existing hook for file-header/style conventions (`"use client"` first line,
  `useState`/`useEffect` from `"react"`).

## 2. Scope

### `app/hooks/useThemeMode.ts` (new)

```tsx
"use client";

import { useEffect, useState } from "react";

export type ThemeMode = "light" | "dark";

const STORAGE_KEY = "guitar-tabs-theme";

function getInitialMode(): ThemeMode {
  if (typeof window === "undefined") return "dark";
  const stored = window.localStorage.getItem(STORAGE_KEY);
  if (stored === "light" || stored === "dark") return stored;
  return window.matchMedia("(prefers-color-scheme: dark)").matches ? "dark" : "light";
}

export function useThemeMode(): { mode: ThemeMode; toggle: () => void } {
  // Seeded "dark" on the server (matches today's hardcoded default, so SSR
  // and first client render agree — no hydration mismatch), corrected to the
  // real stored/system value in the effect below, client-only.
  const [mode, setMode] = useState<ThemeMode>("dark");
  useEffect(() => {
    setMode(getInitialMode());
  }, []);
  const toggle = () => {
    setMode((prev) => {
      const next: ThemeMode = prev === "dark" ? "light" : "dark";
      window.localStorage.setItem(STORAGE_KEY, next);
      return next;
    });
  };
  return { mode, toggle };
}
```

**The `useState("dark")` + effect-correction shape (not `useState(getInitialMode())` directly) is
deliberate, not extra ceremony — embed this reasoning, it's the one real correctness risk in this
task:** `getInitialMode` reads `window`, which doesn't exist during server rendering. Calling it
directly as the `useState` initializer would either crash on the server or (with a guard) render
`"dark"` on the server and then a *different* value on the client's first render — a hydration
mismatch React will warn about (and can visibly flash). Seeding `"dark"` unconditionally (matching
today's actual hardcoded behavior) keeps server and first-client-render identical, then the
`useEffect` corrects to the real stored/system value immediately after mount, client-only. This
produces one unavoidable flash from dark to light for a light-mode user on first paint — accepted,
not a bug to chase (no SSR cookie-based theme plumbing exists in this project, and adding one is
real scope this task doesn't need).

### `app/app/_components/ThemeToggle.tsx` (new)

```tsx
"use client";

import { useThemeMode } from "../../hooks/useThemeMode";

export function ThemeToggle() {
  const { mode, toggle } = useThemeMode();
  return (
    <button
      type="button"
      onClick={toggle}
      aria-label={`Switch to ${mode === "dark" ? "light" : "dark"} mode`}
      className="text-sm text-foreground/70 hover:text-foreground"
    >
      {mode === "dark" ? "Light mode" : "Dark mode"}
    </button>
  );
}
```

Label reads as an action ("Light mode" while dark, meaning "switch to light") — matches how a
plain text toggle button reads most naturally without adding an icon dependency this project
doesn't have. If a reviewer wants an icon instead at staging time, that's a cheap follow-up, not
grounds to block this spec.

### `AppHeader.tsx`

Import and render `<ThemeToggle />` inside the existing `<header>`, alongside the `TabbyTab` link
— `AppHeader` itself **stays a server component** (no `"use client"` added to it); `ThemeToggle`
is the client boundary, imported into a server component the same way any client leaf already
would be in this codebase. Reasonable layout: `justify-between` on the header so the toggle sits
at the opposite end from the wordmark.

### `StudioShell.tsx`

Add `"use client"` as the first line (it now owns `mode` state via the hook and sets
`data-theme` dynamically) — `sidebar`/`detail` stay opaque `ReactNode` props passed through
unchanged, so whatever server-rendered content they contain is unaffected (a client component can
render server-rendered children passed as props — this is the standard, already-established
pattern for this exact reason, not a new technique). Replace:

```tsx
<div data-theme="dark" className="...">
```

with:

```tsx
const { mode } = useThemeMode();
// ...
<div data-theme={mode} className="...">
```

## 3. Non-goals

- No token/build changes — the CSS for both themes already exists.
- No SSR-aware theme (cookie-based first-paint correctness) — the one-flash tradeoff in §2 is
  accepted, not fixed here.
- No icon/animation on the toggle — plain text, matches `DESIGN.md`'s "no decorative motion" rule
  trivially by not having any.
- `DetailToolbar.tsx` is not touched — already resolved as the wrong home for a global toggle.

## 5. Acceptance criteria

- `npm run verify` passes. No automated test required — a `localStorage`-backed hook + a DOM
  attribute has no meaningful unit-test surface in this project's `node --test` runner (no DOM
  harness), and the actual behavior worth checking (does it look right, does it persist across a
  real reload) is exactly what §"Human checkbox" below covers — not something to force into a
  fake unit test for its own sake.
- Per `docs/WEB_APP_WORKFLOW.md` §3's Playwright rule: this *is* interaction behavior (a toggle
  that changes state and persists), not pure visual judgment — but the actual pixel-level
  question ("does every view read correctly in both themes") is a human judgment call this
  project's e2e setup can't verify, and the interaction part (click toggle → attribute flips →
  persists across reload) is small enough that a scripted check would mostly duplicate what a
  15-second manual check already covers with more confidence. **Human checkbox instead, not a
  Playwright spec** — flag this explicitly as the reasoned exception, not a silent skip of the
  standing rule.
- `git diff --stat` matches the allowlist exactly.
- **Human checkbox:** toggle in the browser; reload the page, confirm it persisted; confirm every
  view (Sheet/Fretboard/ASCII, the `/design-system` editor itself) reads correctly in both modes —
  first time light mode is seen live, so this doubles as informal QA of every generated light
  value from Tasks 1/1b onward.
- Self-check before reporting, per `docs/WEB_APP_WORKFLOW.md` §5 step 4's evidence format.
- Checkpoint commit (not pushed).
