# app/ — the Next.js practice-tab website

**Status:** deployed and live at **https://app-six-psi-70.vercel.app** (2026-09-08), confirmed rendering real data from the database. Reads live from the Turso database (`s05_publish` writes to it); currently has a homepage (song list) and a per-song page (renders the ASCII tab). See `docs/ARCHITECTURE.md` for how this fits the whole system, `docs/DECISIONS.md` for why Turso/Drizzle specifically.

**Deploy details:** Vercel CLI (`npx vercel`), no plugin/dashboard-only setup. `vercel link` auto-connected the GitHub repo. `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` added via `vercel env add <name> production` (production scope only, server-side — never `NEXT_PUBLIC_`), verified with `vercel env ls production` before deploying.

**Auto-deploy on push turned off, on purpose (2026-09-08).** `app/vercel.json`'s `git.deploymentEnabled: false` stops Vercel from building anything — production or preview — on any `git push`, on any branch. This is a deliberate decision, not a bug: it fully decouples "committed to GitHub" (every push, always, same as any other commit) from "live on Vercel" (only when explicitly chosen), so ordinary iteration on `master` never spends a Vercel build. If a future need arises for automatic preview deploys on a specific branch (e.g. a `staging` branch), `git.deploymentEnabled` also accepts a per-branch object (minimatch patterns) instead of a flat `false` — see the [Vercel docs](https://vercel.com/docs/project-configuration/git-configuration#git.deploymentenabled) — don't just delete this setting to get previews back.

**To actually deploy a version, run `npx vercel deploy --prod --yes` from the repo root — not from inside `app/` anymore (2026-09-08 correction).** Earlier the same day this was documented as running from inside `app/`; that broke the moment Root Directory was set to `app` on the Vercel project (see the incident above) — a CLI deploy from inside `app/` then double-applies the Root Directory, uploads looking for `app/app/app/`, and fails with "Couldn't find any `pages` or `app` directory." Per [Vercel's own guidance](https://vercel.com/docs/builds/configure-a-build#root-directory) once Root Directory is set: deploy from the actual repo root with a bare `vercel` command, and let that setting do the descending into `app/`. This needed its own project link at the repo root (`.vercel/project.json`, copied from `app/.vercel/project.json`, gitignored, same project ID) and its own `.vercelignore` at the repo root — deploying from the repo root uploads the repo root by definition, and it turned out **not** to reliably honor the repo's own `.gitignore` for exclusion (a first attempt tried to upload 1.9GB, `.venv/` and all, before `.vercelignore` was added — caught before it finished, not after). `.vercelignore` mirrors the same real exclusions (`.venv/`, `pipeline_runs/`, model caches, source audio) explicitly, rather than assuming `.gitignore` is enough for this specific path.

**Incident, fixed (2026-09-08): GitHub-triggered production deploys were broken for 3 deployments in a row.** Every deployment triggered by a GitHub push (not `vercel deploy` from the CLI) failed at the TypeScript check step with `Cannot find module '@/...'` errors for files that genuinely existed and were correctly committed — misleading, since the bundler step immediately before it had already resolved those same `@/` imports fine. Root cause: the Vercel project's **Root Directory** setting was unset (`.`, i.e. the repo root), even though the Next.js app lives in `app/`. CLI deploys never hit this because `vercel deploy` is run from inside `app/` directly and doesn't depend on that setting; GitHub-triggered builds clone the whole repo and need it to know where to `cd`. **Fix:** set Root Directory to `app` in the Vercel dashboard (Project → Settings → General). Re-verified by redeploying the exact same previously-failed commit (`edaaba2`) via `vercel redeploy` — clean `Finished TypeScript` with zero errors, deployed and confirmed live at the production URL. If a future GitHub-triggered deploy fails with `Cannot find module '@/...'` again, check this setting first before assuming a code problem.

**Separately observed, not a code bug:** one CLI deploy during the above investigation failed differently, with `useSearchParams() should be wrapped in a suspense boundary at page "/404"` while prerendering the auto-generated `/_not-found` page. Nothing in this app's own code uses `useSearchParams` (checked). A redeploy of the same source 68 seconds later succeeded cleanly. Read as Next.js 16.3.4's Turbopack production-build path being occasionally flaky on the auto-generated not-found page, not something this repo needs to fix. Worth knowing about if a deploy ever fails with that exact message — retry before investigating further.

**Security review: done (2026-09-08), clean.** No findings — parameterized queries throughout, secrets never reach client code, no `dangerouslySetInnerHTML`, no hidden write routes. This result is specific to the app's current fully-read-only, no-auth shape — see `docs/PENDING_ACTIONS.md` for the standing reminder to re-review if that ever changes.

**Analytics: PostHog, minimal configuration (2026-09-08).** The client records only page views when `NEXT_PUBLIC_POSTHOG_KEY` is configured. Autocapture, session replay, page-leave tracking, person profiles for anonymous visitors, and persistent browser storage are disabled. The public browser project key and US ingestion host are configured in the ignored local environment file and in Vercel production. `.env.example` documents the two required values; use the EU host instead if the PostHog project is ever moved there. The browser project key is deliberately public; do not put a PostHog personal API key or any other secret in a `NEXT_PUBLIC_` variable. **Confirmed working live (2026-09-08)** once the deploy incident above was fixed — pageviews are recording real visits. **Session recording (`disable_session_recording: true`) is off by design, reconfirmed the same day, not a bug** — leave it off unless there's an explicit decision to turn it on (real privacy tradeoff: session replay captures on-screen behavior, not just a pageview, on an app with no auth/consent flow).

**Stack:** Next.js 16.3.4, TypeScript, Tailwind CSS, App Router. Node v26.3.1 / npm 11.16.0 (already on this Mac, no install needed). Auto-generated `AGENTS.md`/`CLAUDE.md` in this folder are Next.js's own version-compatibility notes (regenerated by `next dev`) — unrelated to, and don't override, the repo-root `AGENTS.md`.

**Run it:** `npm run dev` from inside `app/` (needs `app/.env.local` with `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` — already present, gitignored).

**Database access:** `db/schema.ts` (the one table: `songs`) and `db/client.ts` (the Drizzle+libSQL client). Schema changes: edit `db/schema.ts`, then `node --env-file=.env.local node_modules/.bin/drizzle-kit push` (plain `npx drizzle-kit push` won't see the env vars — `drizzle-kit` doesn't auto-load `.env.local` the way Next.js itself does).

**Known, accepted issue:** `npm audit` reports 4 moderate vulnerabilities, all from `esbuild` via `drizzle-kit`'s dependency chain (a dev-server CORS issue). This only affects local schema-migration tooling, never the deployed app. Decided to leave as-is rather than accept `npm audit fix --force`'s breaking `drizzle-kit` downgrade — don't "fix" this reflexively if it resurfaces.

**Design system: in progress (2026-09-08), local-only by design.** `app/design_system/index.html` is a standalone, gitignored playground for tuning color/radius/spacing tokens against mocked-up versions of the real components (song row, tab block), with a live CSS-output panel shaped to paste straight into `globals.css`'s `@theme` block. It's a plain static HTML file — open it directly in a browser, no dev server needed. Deliberately never pushed to GitHub (see `app/.gitignore`) since it's a personal tuning tool, not part of the shipped app; this note exists so a future session isn't confused by a folder it can't see on GitHub. **Planned next (not built):** a live "bridge" mode — the tool embeds the real `npm run dev` server in an iframe and pushes token changes into it via `postMessage`, so tweaks preview against the actual rendered app (real Tailwind output, real components) instead of a hand-built mockup, without ever touching the live/deployed site. Needs a small dev-only listener in the app itself, gated to never run in production. Once real Tailwind components (e.g. shadcn/ui) exist, Storybook is the natural next step up from this tool — deliberately deferred until there's an actual component set worth isolating.

**Fretboard diagram: done, first version (2026-09-08).** `components/FretboardDiagram.tsx`, shown on a song's page below the ASCII tab. Static overview — every unique string/fret position used anywhere in the song, deduped, drawn once — with a toggle to flip which string (thin e vs thick E) is on top. Pure logic (fret range, position dedup, display-row mapping, pitch-class naming) lives in `lib/fretboard.ts`, unit-tested in `lib/fretboard.test.ts` via Node's built-in test runner (`npm test` → `node --test`) — no new dependency, and the first real test this app has had. Colors are hardcoded (not yet wired to the `design_system/` tokens above — that's a real follow-up, not an oversight) but explicitly backgrounded (`bg-white`) rather than inheriting the page's theme, since the surrounding page doesn't consistently support dark mode yet either and a transparent card nearly disappeared against it during testing — caught and fixed before this was called done, not discovered later. See `docs/DECISIONS.md`'s "Display modes are layered" section for the fuller reasoning and the deliberately-not-built sequential/step-through version.

**Not built yet:** playback/metronome/note-highlighting, any local-processing UI (still CLI-only), the design system above isn't applied to the real pages yet (including the new fretboard diagram), a sequential/step-through fretboard view, CI.
